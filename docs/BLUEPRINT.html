Agentic RM Workbench

A single-page workbench that turns 20 client files, five portfolio snapshots and sixteen world events into a ranked list of what Priscilla Ong should do this morning, this week and this month, with every recommendation traceable to the evidence that produced it and a machine-checked confidence score beside it.

How to read this document. It is the full product scope we agreed to discuss before building. Each section ends in something concrete: a screen, a table, an engine, or a decision. Section 10 breaks the scope into build iterations; we review one iteration at a time.

01Vision and non-negotiable principles

The dataset README states the goal plainly: move the RM from "what does the portfolio look like" to "what should I know and what should I do next". The wireframe deck adds three operating rules. We adopt all of them as product constraints, not aspirations.

Scan in 30 secondsThe RM cockpit shows the KPI strip, the risk banner and the action queue without scrolling. Nothing on L1 needs a click to be understood.
Evidence before recommendationEvery signal, score and trade idea carries its source rows, its model, and its confidence before any action button appears.
Human approval for every actionNo automated trading. The RM reviews, approves or rejects, and every decision is written to an immutable audit log with maker-checker where required.

Two additional rules from the dataset

The event log is the only source of world events. Claude never free-associates about 2026 geopolitics. Explanations cite event IDs from the event log and series from the market context table. If the model wants to reference something outside those files, the explainability layer marks it as an unverified claim.

Honesty about uncertainty is a feature. Where the data cannot support a conclusion, the workbench says so and lists what the RM would need to check. The judging notes reward this explicitly.

03Information architecture: two views, three levels

The workbench is one single-page application with two top-level views. Each view is layered so that L1 answers "what needs my attention", L2 answers "why, and how sure are we", and L3 exposes the raw evidence and model internals. The same three-level contract applies to every card, chart and recommendation, which is how explainability becomes a habit rather than a feature.

L1Attention
  • Ranked queues: Now · This week · This month
  • KPI strip and composite risk gauge
  • Severity pills, deltas since last snapshot
  • One-line plain-English insight per item
"Who do I call first, and why in one sentence?"
L2Reasoning
  • Evidence drawer: source rows, event IDs, market series
  • Rubric scores with observed behaviour
  • Impact waterfalls and assumptions
  • Confidence breakdown: rules · LLM · statistical model · data quality
"How was this reached, and could I defend it to the client?"
L3Evidence & audit
  • Raw holdings, transactions, notes behind a claim
  • Model parameters, prompts, validator outputs
  • Snapshot-by-snapshot trajectory tables
  • Immutable decision and override log
"Show me the exact numbers and the exact prompt."

05Intelligence engines

Seven engines sit between Postgres and the UI. Each is a pure function of database state plus a run timestamp, writes its output back to versioned tables, and exposes an explanation object that the UI renders at L2 and L3. Claude is used where language and judgement are needed; deterministic Python is used wherever a number can be computed.

Customer Vectorcustomer_vector · nightly + on demand

Two artefacts per client. Factual data is a normalised record: demographics, domicile versus residence, wealth band, mandate, stated risk profile and score, horizon, liquidity needs, objectives, life stage, KYC status, planned cash needs, facilities, commitments.

Behavioural vector is a fixed-order numeric vector computed from holdings and transactions across the five snapshots. Initial feature set:

  • Cash buffer %, cash buffer trend, withdrawal frequency and unplanned-withdrawal count
  • Portfolio volatility proxy, max drawdown across snapshots, behaviour in drawdown (added, held, sold)
  • Turnover, average holding period, share of tactical versus core positions
  • Concentration: top-1 and top-3 weight with look-through, source-of-wealth overlap flag
  • Liquidity runway: daily-liquid assets divided by 12-month confirmed cash needs
  • Leverage: LTV, utilisation, LTV slope over five snapshots
  • Mandate drift velocity, days to nearest cash need, days to KYC due

An LLM-derived narrative embedding of the RM notes is stored alongside in pgvector for similarity search and chatbot retrieval. The behavioural vector, not the embedding, drives the rubric.

Risk Rubricrisk_rubric · Capacity · Appetite · Horizon

Scores each dimension 1–3 exactly as the wireframe defines them. Three independent assessors produce a score with evidence; agreement between them becomes the confidence.

  • Rules assessor (Python): thresholds on vector features, for example Capacity 1 when cash buffer under 5% or two unplanned withdrawals in six months.
  • LLM assessor (Claude): reads the factual record, the vector with feature descriptions, and the RM notes; returns a structured score, cited evidence, and a stated-versus-observed mismatch flag.
  • Statistical assessor (Python): a calibrated classifier over the vector, described in section 6.

Output includes the mismatch warning ("Portfolio risk exceeds Appetite score") and the RM override slot. Scores are versioned; the client's stated risk profile from the client file is shown next to the behavioural score so the tension is visible.

Signal Enginesignals · replayed from event_log + market_context

Converts the 16 events and 23 market series into typed signals with severity, transmission channels and the client exposures they touch. A simulation clock replays signals so the feed feels live during a demo while remaining fully grounded. Each signal maps its transmission channels to instruments through sector, region, sub-asset class and structured-product underlying reference.

Confidence is decomposed the way the wireframe shows it: data freshness, source reliability, model confidence. For this dataset "source reliability" is 100% for event-log items and marked lower for any derived signal.

Impact Engineimpact · deterministic stress models

Runs the stress waterfall. Models are simple, stated on screen, and computed in Python so they can be validated:

  • Rates: modified duration × yield change per bond, duration estimated from maturity and coupon
  • FX: notional × spot move for each instrument currency against portfolio base currency
  • Equity: beta-adjusted index move by region and sector, with a technology and energy overlay
  • Structured products: payoff approximation from the underlying reference and barrier terms
  • Collateral: recompute lending value and LTV after the shock, flag trigger breaches
  • Liquidity: post-shock daily-liquid assets against confirmed needs in the next 12 months

Base, mild and severe scenarios plus a named library: Strait reopens, escalation, Fed hike, tech drawdown repeat. Claude writes the narrative and the "assumptions" paragraph but never the numbers.

Trade Ideastrade_ideas · signal × portfolio × rubric

Candidate ideas are generated by rules (reduce duration where horizon is short and rates rose; hedge currency mismatch where obligations differ from asset currency; trim single names over the limit; replace excluded holdings in sustainable mandates; raise cash where liquidity runway is under 12 months). Claude then ranks and explains them for the specific client, in the client's framing from the notes.

Every idea passes a suitability gate: within mandate bands after the trade, respects single-position limit, respects exclusions, respects liquidity tier versus need date, respects the rubric. Failed ideas are shown with the failing rule rather than hidden, because the RM should see what the system considered.

Horizon Enginehorizon · Now · 7 days · 30 days

Assigns each open item to a lane using trend across the five snapshots rather than a static threshold. Examples from the data:

  • Now: LTV within 1 point of trigger or crossed it in the last two snapshots (Ravi, Lau); client message unanswered more than five days (Chalermchai, 19 Aug); KYC overdue (Tan, 31 Aug).
  • 7 days: KYC due within 14 days (Chen, 11 Sep); confirmed cash need starting within 30 days (Nguyen's US fees, Aishah's Australian fees, both Sep 2026); meetings in the fortnight.
  • 30 days: cash needs starting within 90 days (Voss-Brenner EUR 3.4m from Oct); capital call windows opening (Fong, Q4 2026); mandate drift whose velocity will breach a band within one snapshot interval.

Each card records why it is in its lane and the lane it would have held one snapshot earlier, so the RM sees momentum, not just state.

Assistantchat · Claude with typed tools

A tool-using agent. Tools are narrow and read-only against Postgres and the analytics service: get client, list holdings with look-through, compare snapshots, list transactions, get mandate status, run impact scenario, search notes, list events. Writes (approve, override, draft outreach) go through the same API the UI uses and still require the RM's click.

The system prompt injects the event log as the only permitted world knowledge. Every reply carries the tool trace, which the UI renders as the L3 for that answer.

06Confidence scoring and explainability

The brief asks for predictive Python code that validates LLM outputs and shows a confidence score. With twenty clients there is no honest way to train a supervised model on real labels, so the design is transparent about what the score means.

What the confidence score is

A weighted agreement measure between independent assessors, penalised for data quality and staleness:

confidence = 0.45·agreement(rules, llm, stat) + 0.25·stat_calibrated_prob + 0.15·data_quality + 0.15·freshness
  • Agreement is 1 when all three assessors return the same rubric score, 0.6 when two agree, 0.2 when all differ. For numeric outputs (impact estimates) it is 1 minus the relative gap between the LLM's stated figure and the Python recomputation.
  • Statistical assessor is a gradient-boosted classifier trained on a disclosed archetype simulation: several thousand synthetic behavioural vectors generated from the rubric definitions themselves, with noise, then isotonic-calibrated. It cannot know things the rules do not encode, and the UI says so. Its value is catching an LLM score that the numbers do not support.
  • Data quality drops for stale valuation dates, missing cost basis, custody accounts mixed into mandate checks, and entity clients without demographic fields.
  • Freshness follows the wireframe rule: full credit under 15 minutes on the simulation clock, decaying afterwards, with the stale-data warning shown above 15 minutes.

Explainability contract

Every insight object stored in Postgres carries the same shape, and the UI renders it identically at every level:

insight ├── headline L1 · one sentence, plain English ├── severity, lane L1 ├── confidence L1 number · L2 breakdown ├── reasoning[] L2 · ordered steps, each citing evidence ids ├── evidence[] L2 · {table, row_ids, fields, values} ├── models[] L2 · {name, version, parameters, output} ├── assessors L2 · rules / llm / stat scores side by side ├── caveats[] L2 · what the data cannot tell us ├── llm_trace L3 · prompt hash, model id, response, tokens └── lineage L3 · run id, snapshot date, inputs hash

The stated-versus-observed comparison is a first-class field: the client file says Growth 8/10, the behaviour says Appetite 3/3, the note says "agitated about the drop". When they disagree the workbench shows all three rather than picking one.

09Engineering standards

The brief asks for stringency on code quality and structure. These are the rules the codebase will be held to from the first commit.

Area Standard
Language and types TypeScript strict mode everywhere; no any. Shared Zod contracts generate the types used on both sides. Python typed with pydantic models and mypy in strict mode.
Structure API in route → service → repository layers; engines are pure modules with explicit inputs and outputs; no SQL in route handlers; no business logic in React components.
Testing Vitest for TypeScript, pytest for Python. Engines and impact models tested against hand-computed fixtures from the dataset, for example the Ravi LTV path and the Voss-Brenner mandate breach. Contract tests between API and analytics service.
LLM discipline All prompts live in a registry with versions. Structured outputs validated against schemas; a failed validation is an error, never silently accepted. Every call traced. Numbers in narratives are injected from computed values, not generated.
Linting and formatting ESLint with typescript-eslint strict, Prettier, Ruff for Python. Pre-commit hooks. Conventional commits.
Security API key only from environment. No client data in logs. Read-only tools for the assistant. Rate limits on LLM endpoints. Synthetic-data notice retained in the README.
Documentation Architecture decision records for each major choice, a data lineage note per derived table, a demo script, and a README that runs in three commands.

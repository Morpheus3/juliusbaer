Agentic RM Workbench · data platform

Data Platform Assessment

You asked whether the project has a data pipeline, what the database looks like, and what is missing to ingest from Kafka or batch, onboard new customers and new RMs, and keep one RM's clients invisible to another. This is the honest state and the design for the rest.

01Short answer

There is a batch pipeline, not a streaming one. A seed command reads one dataset folder of CSV and JSON, validates every row against Zod contracts, truncates and reloads the raw schema, runs thirteen data-quality checks, loads the reference files, and records the run. The customer vector is built by the Python analytics service on demand from Postgres and persisted with a run id. Every engine reads from Postgres, never from files.

There is no Kafka consumer, no incremental upsert, no per-client rebuild, no identity, no RM entitlement. The RM is inferred as "the RM covering most clients" because the dataset has one. The API has no login; every request sees every client.

The schema is ready for the change. Every client-owned table already carries a client id, clients already carry an RM id, and the derived tables already record which run produced what. Adding RMs, assignments, identity and row-level security is additive; the engines do not change.

02The pipeline as it stands

1SourceOne folder: 11 CSV files (clients, portfolios, holdings by snapshot, transactions, facilities…), notes as JSON, and reference/*.json. Path from DATA_DIR.
2ValidateRow schemas in @jb/contracts (Zod); wide snapshot columns discovered by regex. Bad rows stop the load.
3Loadraw.* truncated and repopulated in one transaction. A load_runs row records counts, status and "today" (latest snapshot).
4Quality13 checks (orphans, weights, stale marks, exclusions held, needs parity…) → data_quality_issues, visible in the Audit room.
5Referencelook-through legs, signal rules, scenarios, call policy, cross-border doc → derived.*; missing files degrade gracefully.
6VectorPOST /vectors/build on the analytics service reads Postgres, computes 32 features, percentiles, peers, note embedding; writes vector_runs, client_factual, client_vectors.

Everything after step 6 is computed at request time from raw and derived tables: alerts, lanes, signals, impact, rubric, actions, ideas, call plan, promises. That is why the engines are dataset-agnostic and why a new pipeline only has to land correct rows.

Two things to notice. The derived tables reference clients by id but without a foreign key, deliberately: a client can be reassigned or offboarded without breaking the audit trail. And nothing in the derived schema names an RM except overrides and actors, so entitlement has to come from the raw side.

06Target design

One ingestion module with two front doors, a landing schema, incremental loads into the same raw tables, and change events that drive the vector and the alerts. The engines stay as they are.

AFront doorsKafka consumer (one topic per entity: clients, rm-assignments, holdings-snapshot, transactions, facilities, notes, prices, events) and a batch drop (the current folder format, or files on an object store). Both produce the same typed messages.
BContractsMessage schemas in @jb/contracts beside the row schemas, versioned; each message carries entity id, event time, source system, and an idempotency key (source + sequence).
CLandingstaging.* tables: raw message, key, received_at, status. Bad messages stay here with the validation error and go to a dead-letter view; nothing bad reaches raw.
DApplyUpsert by natural key into raw.*; snapshot tables append by (id, snapshot_date); deletes become valid_to timestamps. One transaction per batch or per message group; a load_runs row per apply.
EChange eventsA change_log table (client_id, entity, kind, applied_at). The analytics service subscribes (poll or NOTIFY) and rebuilds the vector for changed clients; a nightly job rebuilds all so percentiles and peers stay consistent.
FQualityThe thirteen checks run per batch scoped to changed clients, plus reconciliation counts against the source manifest; failures do not block the apply, they surface in the register and on the manager's page.

Why an assignment table and not a column. Clients move between RMs; a checker is a second RM on the same client; a team head covers by team, not by client. A dated assignment row answers "who may see this client today" and "who saw it in March", which the audit trail needs. The rm_id column on clients stays as a denormalised current primary for the engines that read it, kept in step by the apply step.

07RM isolation in depth

Isolation must be enforced where the data lives, not only in the queries an engineer remembered to filter.

1 · Identity on every request

The API takes a bearer token (the bank's OIDC), verifies it, and resolves user → rm_id and roles. DatasetContext stops guessing the RM; the meta endpoint returns the caller's RM and scope. RM_LEVEL and CHECKER_ID leave the environment and become roles and assignments.

2 · Row-level security in Postgres

Every client-owned table in raw and derived gets an RLS policy: a row is visible when its client_id is in the caller's entitled set. The API sets set_config('app.rm_id', …) and app.scope per transaction; a SQL function computes the entitled set from rm_assignments (own book), teams (team head) or all (admin). A query that forgets a filter still returns only what the caller may see.

3 · Repositories filter too

Belt and braces: ClientRepository.listAll becomes listEntitled(ctx), and every per-client repository call checks entitlement before reading, returning 404 rather than 403 so client ids cannot be probed.

4 · Derived data follows the client

Vectors, rubric, promises, decisions and audit events carry client_id, so the same policy covers them. Percentiles and peers are computed across the whole book by the analytics service under a service role; what the RM sees is her clients' percentile against the book, not other clients' rows.

5 · The assistant respects scope

findClients, compareClients, the call plan and the idea desk run over the entitled set only; the tool catalog receives ctx, not a book. The team head's scope is the team; "who should hear about the Fed hold" then answers for the team.

6 · Audit and traces

actor becomes the authenticated user; LLM traces record the entitled scope used. A manager sampling explainability sees traces for the team only.

10Decisions for you

Q1 · Where does identity come from?

The bank's OIDC in production; for the hackathon, a development provider with a login page and two or three seeded RMs. Recommended: build against OIDC claims from day one, with the dev provider issuing the same claims.

Q2 · Kafka or batch first?

Batch incremental (D3) delivers most of the value and is testable without infrastructure; Kafka (D4) is the same apply module behind a consumer. Recommended: D3 then D4, with Redpanda locally.

Q3 · Isolation strictness

Own book only, or own book plus team for heads, plus a "cover" assignment for holidays. Recommended: all three roles in rm_assignments from the start; they are rows, not code.

Q4 · Percentiles across whose book?

Peers and percentiles across the whole bank give better signal but leak nothing if only the client's own percentile is shown. Recommended: compute bank-wide under a service role, show per client.
